01 The tree, and what you may leave out

An HTML document is a tree of elements, and the parser builds html, head and body whether you type them or not. Every page in this repository omits all three, and every one of them is valid.

the smallest

<!-- this entire file is a legal HTML document -->
<title>A page</title>
<p>Text.

The parser puts <title> in the head it created for you, sees content that cannot live in a head, closes it, opens a body, and puts the paragraph there. The tree is identical to the one you would have got by typing eleven more lines. What you may not leave out is <title> — it is the tab, the bookmark, the history entry and the first thing a screen reader says — and the viewport meta, without which a phone renders your page at 980px wide and shrinks it.

The reason to know this is not brevity. It is that the tree the browser has is not the text you wrote, and every selector you write addresses the tree. An unclosed <li> does not break anything; it closes itself when the next one opens, and your li + li still works. A <div> inside a <p> does break something: the paragraph closes at the div, and your p > div matches nothing, forever, silently.

<div> is not permitted inside <p>, so the parser implicitly closes the paragraph when it meets the div. The tree is p("One") · div("Two") · p(empty) — three siblings, with a stray empty paragraph from your closing tag. The div is never a descendant of a p, so p div can never match it. Nothing warns you.

This is the general shape of the whole first chapter: malformed HTML rarely errors, it re-parents. When a selector that looks obviously correct matches nothing, check the tree in the inspector before you touch the selector. In this yard you can also open any page with ?dev and use PROBE, which lists every rule that matches an element you click — if yours is not in the list, the selector never addressed that node.

02 The label is the control

A <label for="x"> is a click target for the input with id="x", wherever that input is in the document. This is the hinge the entire yard turns on: the input carries the state, the label is the thing you press, and they need not be near each other.

the smallest

<input type="checkbox" id="fly"><label for="fly">Fireflies</label>

.eco input{position:absolute;opacity:0;width:1px;height:1px}
.eco label{cursor:pointer;padding:10px 13px;border:1px solid #333}
.eco input:checked + label{border-color:#4fd18b;color:#4fd18b}

Note what the input is not: it is not display:none. A hidden input is removed from the tree’s layout and from the tab order, so the control becomes unreachable by keyboard and invisible to assistive technology. Moving it off with opacity:0 and a 1px box keeps it focusable and announced, and then input:focus-visible + label paints the focus ring on the part the user can see. Three lines, and the difference between a control and a picture of one.

There is a second consequence, and it is the one this repository is built on. Because the input holds the state and CSS can select on :checked, a checkbox is a boolean the stylesheet can read. Twelve of them is a twelve-bit word. That is the whole trick, and everything from chapter five onwards is arithmetic on it.

display:none generates no box, and an element with no box is not focusable and not exposed to the accessibility tree — so Tab skips it, Space cannot toggle it, and a screen reader never announces there is a checkbox at all. The label still works with a pointer, which is why it looks fine to you.

Replace it with position:absolute;opacity:0;width:1px;height:1px and add input:focus-visible + label{outline:2px solid …} so the ring lands on the visible part. The same fact bites in chapter five for a different reason: an element with display:none generates no box, so it also increments no counter — which is either a bug or the mechanism, depending on whether you meant it.

03 The cascade, in the order it is decided

When two rules set the same property on the same element, the winner is decided in this order and it stops at the first difference: origin and importance → layer → specificity → source order. Source order is last. It only settles ties.

the smallest

.board .cap        { display:none }   /* written last  */
.board:has(#a:checked):has(#b:checked) .cap { display:block }
/* the second one wins anyway: (0,4,0) beats (0,2,0) */

This is the mistake that cost this repository a real bug and it is worth the paragraph. A blanket “stop” rule was written at the foot of ecosystem.html on the assumption that being last would carry it. It was .eco:not(:has(#fly:checked)) .cap, specificity (1,3,0), and every capability rule it was meant to override was a compound :has() at (2,4,0). It lost to all of them, silently, and a rule that loses looks exactly like a rule nobody wrote.

The fix was not !important. Reaching for importance to win a fight you lost on specificity buries the disagreement instead of settling it, and the next person inherits a stylesheet where the real precedence is invisible. The fix was noticing the claim was false — two of those capabilities genuinely do survive losing the clock, so the blanket rule should never have existed. The arithmetic is still nailed to the foot of that stylesheet as a warning.

A wins. A is (1,1,0) — one id, one class. B is (0,4,0) — four classes, zero ids. The comparison is lexicographic on the triple: one id beats any number of classes, so the first column decides it before the second is even read, and being two hundred lines later is worth nothing. This is the single most common cascade surprise there is.

And yes, a layer changes it completely — layers are compared before specificity, not after. If A sits in @layer base and B sits outside every layer, B wins with its four classes, because unlayered styles beat layered ones outright. That is the point of layers: it lets you put a third-party sheet in a low layer and stop fighting its ids with ids of your own.

04 Specificity, counted properly

Specificity is a triple (a, b, c) compared left to right: a = ids, b = classes, attributes and pseudo-classes, c = element types and pseudo-elements. Combinators and the universal selector count for nothing.

the smallest

#a              (1,0,0)      .a.b.c.d.e.f  (0,6,0)   ← still loses
.a:hover        (0,2,0)      a[href^="#"]  (0,1,1)
:has(.x)        (0,1,0)      :has(#x)      (1,0,0)   ← inherits!
:is(p, #q)      (1,0,0)      :not(.x)      (0,1,0)
:where(#q)      (0,0,0)      *             (0,0,0)

The three that catch people: :has(), :is() and :not() take the specificity of their most specific argument — so :is(p, #q) is as heavy as an id even when it matched the p. :where() contributes zero, always, which makes it the tool for writing a default you actually intend to be overridden. And inline style= is not a specificity at all — it is a higher origin, and only !important in an author sheet reaches past it.

You do not have to count by hand. Open any page in this yard with ?dev, arm PROBE, and click an element: every rule that matches it is listed in source order with its triple computed, and the one that is actually winning is the one you can now see rather than guess.

First: .eco is a class (b+1). :not(…) takes its argument’s specificity, and the argument is :has(#fly:checked), which takes its argument’s — #fly is an id (a+1) and :checked a pseudo-class (b+1). Then .cap is another class (b+1). Total (1,3,0).

Second: .eco (b+1), two :has() each contributing an id and a pseudo-class (a+2, b+2), and .c-prove (b+1). Total (2,4,0).

The second wins, on column a — two ids to one. The comparison never reaches the classes. These are the exact selectors from ecosystem.html, and this is the arithmetic that was not done before the rule was written.

05 Counters are arithmetic

CSS counters add. counter-reset declares one, counter-increment adds to it, content:counter(n) prints it — and a counter can only print a value that something earlier in the document already added. That single sentence is the whole discipline.

the smallest

body            { counter-reset: ayes 0 }
.seat.aye       { counter-increment: ayes 1 }
.total::after   { content: counter(ayes) }

<div class="seat aye"></div>   ← must come FIRST in the DOM
<div class="total"></div>      ← or this prints 0

The ordering constraint is not a quirk, it is the definition: counters are resolved in document order during layout, so a ::after shows the running value at that point in the tree. Put the tally above the things it tallies and it prints zero, correctly, forever. Every board in this yard that shows a total therefore has its inputs physically above the total in the source, and the ones that need a tally at the top solve it by putting an invisible strip of state first — see the store in persist.html.

The second constraint is chapter two’s fact wearing a different hat: an element with display:none generates no box, so it increments nothing. Which is a bug when you meant to hide something visually, and a mechanism when you meant a capability to stop counting itself the moment it is unavailable. Use visibility:hidden when you want it hidden but still counted.

The 12, yes. The 3, no — not there. A constant needs no arithmetic: reset it to 12 on body and print it anywhere. But 3 is a sum over elements that come later in the tree, and at the caption’s position in document order that sum is still zero. There is no forward reference and there is no second pass.

Three honest fixes. Move the caption below the boxes and use flexbox order or grid placement to draw it above — layout order and document order are independent, and this is the right answer nearly every time. Or duplicate the state into a hidden strip at the top of the document, which is what persist.html does, at the cost of writing the state twice. Or enumerate it with compound :has(), which is chapter seven and costs you every combination written out by hand.

06 :has() is state

:has() selects an element by what is inside it, or after it. It is the parent selector, the previous-sibling selector and the “any descendant matches” selector at once — and it is what turns a checkbox from a decoration into a variable the whole stylesheet can read.

the smallest

.board:has(#fly:checked)  .lantern { opacity:1 }      descendant
.row:has(> .err)          { border-color:#e0705a }   direct child
label:has(+ input:checked) { color:#4fd18b }          next sibling
.form:has(:invalid)        .submit { opacity:.4 }     any descendant

Before :has(), state in CSS travelled only downwards and sideways — :checked + label and :checked ~ .thing — which meant every element that needed to react had to be a later sibling of the input. That is why pre-2023 CSS demos are full of inputs jammed at the top of the markup in an order dictated by the stylesheet. :has() reaches upward, so the input can go where it belongs and any element on the page can ask about it.

Two things to hold on to. It never matches the descendant, it matches the ancestor — .a:has(.b) styles .a, and forgetting that is the commonest first mistake. And it is not cheap but it is not slow either: the engine only re-evaluates it when something inside the subject changes, so a page with 1,500 :has() rules — this yard has more — is fine. Do not put it on * and do not nest it four deep for sport.

The rule is .drill:has(input:checked) .ans{display:block} — the drill asks whether its own checkbox is checked and reveals its answer. The checkbox lives in the drill; the answer lives in the drill; :has() is the only thing that lets the second know about the first without them being siblings in a fixed order.

display:none rather than a collapsed height because a zero-height overflow-hidden panel is still in the accessibility tree and still focusable — a screen reader reads all twelve answers, and Tab lands inside a box the user cannot see. It also cannot animate honestly to auto without calc-size(), which is new. Correctness first: if it is hidden, hide it.

07 Compound :has() is a lookup table

CSS has no multiplication over state. So when an outcome depends on two or three inputs together, you do not compute the product — you write the products out. Three inputs by four options is twelve rules, and someone typed every one of them.

the smallest

/* reading × circuit × hour → the instrument's weight.
   There is no expression. There is a row per combination. */
.v:has(#plain:checked):has(#sun:checked):has(#dawn:checked) .w::after{content:"14"}
.v:has(#plain:checked):has(#sun:checked):has(#dusk:checked) .w::after{content:"12"}
.v:has(#tech:checked):has(#sun:checked):has(#dawn:checked)  .w::after{content:"11"}
… twenty-one more …

This looks like a defeat and it is worth arguing that it is not. A lookup table is auditable in a way an expression is not: every cell is visible, every cell was a decision, and a reviewer can point at row nine and say that one is wrong without reading any logic. When the table gets long enough to hurt, that is information — it means the model has more state than the thing it is modelling deserves, and the answer is usually to cut an input rather than generate the rows.

Know the ceiling before you start. The cost is the product, not the sum. Two axes of three is nine rules and pleasant; three axes of four is sixty-four and a build step; four axes of five is six hundred and twenty-five and you should have written a script or reduced the model. In this repository the tables are generated from JSON by profiles.mjs and ships.mjs once they pass about twenty rows — the page stays scriptless, the authoring does not have to be.

Enumerating combinations is 2⁴ = 16 rules. But you asked for the count, not the combination, and counting is chapter five: counter-increment on each checked box gives you the number in one rule, and content:counter(n) prints it.

If the message must be prose rather than a number, you need to select on the count, and CSS cannot — so it is either five rules using :has() with the sixteen combinations grouped into five comma-separated selectors, or you accept a number in the sentence. The general lesson: reach for a lookup table only when the outcome genuinely depends on which, not how many. Half the tables people write by hand were a counter.

08 :target is the only durable store

Checked inputs die with the tab. The URL fragment does not — it survives reload, it is in the bookmark, it goes in a message, and Back steps through it. :target is the only selector that can read it, and the query string cannot be read from CSS at all.

the smallest

<a href="#st-b2">berth B, second watch</a>
<i id="st-b2"></i>                        ← the store

.board:has(#st-b2:target) .k-b2 { border-color:#e0b155 }
.board:has(#st-b2:target) .tick{ counter-increment:berth 2 watch 2 }

The price is stated up front because it is not negotiable: a document has one :target at a time. One. So a board with two axes does not get two independent stored values — it gets one value that must name the whole combination, and you enumerate the product exactly as in chapter seven. Three berths by two watches is six ids and six links, and a fourth berth costs you two more of each.

What you get for it is worth listing, because they are all good: reload restores it, a bookmark is a save file, the URL is the whole document, Back is undo and Forward is redo, sharing works, and every state has a name a person can type. What you do not get is the query string. <form method="get"> still hands state to the next page, and that page cannot read ?berth=b in CSS. Nothing can — which is precisely why this yard puts its script layer there. The two halves of a URL are read by two layers that cannot see each other, and that separation is deliberate.

You cannot have both, and the fix is to stop wanting the second. One :target means one stored value. Either the state is one axis with n values, or it is one axis with n×m values whose names are combinations — and the combination table is the honest form, so draw it as a grid of links rather than as two rows of controls that pretend to be independent. The grid is the truth about the store.

The dishonest answers, for completeness: :target plus checkboxes gives you two axes where one survives reload, which is worse than either because the page comes back half-restored. And localStorage is a script, at which point say so plainly and stop calling the page scriptless.

09 Flow, flex, grid — three engines, one question

Every layout problem is: who decides the size? Flow — the content does, and boxes stack. Flex — one axis, the items negotiate. Grid — the container declares the tracks first and the items are placed into them.

the smallest

display:flex   one axis. Use when the items decide the shape:
                a toolbar, a row of chips, a header with an auto margin.
                margin-left:auto on one child pushes the rest apart.

display:grid   two axes. Use when the CONTAINER decides the shape:
grid-template-columns: repeat(auto-fill, minmax(220px, 1fr))
                ↑ responsive with no media query at all

The heuristic that survives contact: if you find yourself setting widths on flex children to line them up with the row above, you wanted grid. Flex has no memory across lines — wrapped rows do not know about each other — so any alignment between rows is grid’s job. Conversely, if you are writing grid-column on every child by hand, you probably wanted flex and a gap.

Two facts that save the most time. gap works in all three now, including flow, so stop putting margins on children to space them — margins collapse, gaps do not, and a gap does not leave a trailing one on the last item. And minmax(0, 1fr) is the fix for the grid child that refuses to shrink: 1fr means minmax(auto, 1fr), and auto floors at the content's minimum size, which is why one long unbroken string blows out a column.

The column is sized 1fr, which is minmax(auto, 1fr), and auto will not go below the content’s min-content width. A <pre> does not wrap, so its min-content width is the whole longest line, and the track is forced open.

Fix one: minmax(0, 1fr) on the track, which lets it shrink below content. Fix two: min-width:0 on the grid item, same effect, applied at the child. Either works; fix two is usually right, because the problem is that one card, not the track definition, and the <pre> also needs overflow-x:auto so the long line scrolls inside its own box instead of the page scrolling sideways. Both fixes without that last bit just move the overflow somewhere less visible.

10 Stacking contexts, and why your z-index does nothing

z-index only compares siblings within the same stacking context. A z-index of 9999 inside a context that itself sits below another context is still below it. And a great many innocuous properties create a context: transform, filter, opacity under 1, will-change, position:fixed, isolation:isolate.

the smallest

/* the yard's sky. Two fixed pseudo-elements BEHIND everything,
   painted before every in-flow background — including body's. */
html::before, html::after {
  content:""; position:fixed; z-index:-1; inset:-18%;
  background-image: … 208 gradients … }
body { background-color: transparent }   ← or it paints over the sky

That last line is the whole lesson in one declaration. Negative-z-index positioned elements are painted before the in-flow block backgrounds of the same context, so html::before does sit behind body’s content — but body’s own background is a solid rectangle over the top of it, and a sky you cannot see is indistinguishable from a sky you did not build. Every page in this yard clears body{background-color:transparent} and keeps its semi-transparent gradient wash, which then composites over the stars instead of erasing them.

The diagnostic, when a z-index does nothing: walk up the ancestors looking for a transform, a filter or an opacity below 1. One of them made a context and trapped your element inside it. The fix is almost never a bigger number — it is moving the element out of that subtree, or putting isolation:isolate on the right ancestor so the contexts are at least explicit and the next reader can see them.

translateZ(0) creates a stacking context on the card’s parent. Everything inside that parent, including your 9999, is now painted as a single unit at the parent’s own level. The comparison the browser is actually making is parent versus modal’s context, and 9999 never enters into it — it only orders the modal against its own siblings.

Fix: move the modal out of that subtree, to a direct child of <body> — which is what a portal is for, and what the native <dialog> element gives you free via the top layer, above every stacking context on the page. Removing the translateZ(0) also works and is usually right anyway: it was a 2014 performance hack, modern engines promote layers on their own, and will-change is the honest way to ask.

11 Custom properties inherit — they are not macros

A custom property is a value on an element that descendants inherit, resolved at use, not a find-and-replace at parse time. Which means you can redefine one on a subtree and everything below it changes, and it means an invalid value fails differently than you expect.

the smallest

:root      { --edge:#28323d; --go:#4fd18b }
.warn      { --go:#e0705a }              rebound for a subtree
.chip      { border:1px solid var(--go) }  resolves per element

/* the theme switch with no script and no duplicated rules: */
:root:has(#dark:checked) { --void:#080a0d; --ink:#e7edf3 }

Because they inherit, one rule can retheme a whole subtree without knowing what is in it — and because they resolve at use, the same var(--go) in a shared component gives a different colour in a .warn than outside it. That is the feature. It is also why a custom property is the right unit for a design token and the wrong unit for a one-off value used once.

Two sharp edges. An invalid substitution is not ignored, it computes to unset — if --go holds 12px and you use it as a colour, the declaration does not fall back to the previous rule the way a normal syntax error would; the property becomes inherited-or-initial, which is usually black or transparent and always confusing. Give fallbacks: var(--go, #4fd18b). And they are not animatable unless you register them with @property and give them a syntax — otherwise the browser has no idea whether it is interpolating a colour, a length, or a word.

Because the sky is injected into fifty-odd pages that do not agree on a variable name. Most define --void; some call it something else; a couple define no palette at all. A var(--void) in the injected block would resolve to unset on those pages — transparent — and the star field would sit on white. The generator reads each page’s own background colour and writes that hex in, so the block is correct against a page it has never seen.

The general rule: a custom property is a contract, and you can only use one where the contract is guaranteed. Inside a component you wrote, always. Injected into documents you do not control, never — resolve it at build time and write the value.

12 What the compositor does for free

Animate transform and opacity and the compositor moves an already-painted layer on another thread. Animate anything else — width, top, background-position, box-shadow — and the main thread relayouts or repaints every frame. This is not a micro-optimisation; it is the difference between 60fps and 6.

the smallest

html { background-image: … 208 gradients …;
       animation: drift 900s linear infinite }   ← repaints 208
@keyframes drift { to { background-position: -30% 12% } }

html::before { background-image: … ; will-change:transform;
               animation: au-far 2040s ease-in-out infinite alternate }
@keyframes au-far { to { transform:translate3d(-3%,1.6%,0) scale(1.09) } }

The struck-out version is what this yard shipped first and it is why the sky is built the way it is. Two hundred and eight radial gradients are expensive to rasterise once; rasterising them every frame because background-position changed is a frame budget spent on wallpaper. Moving the same gradients onto two fixed pseudo-elements and animating transform instead costs one rasterisation, ever, and the movement is a matrix on a layer the GPU already holds. Same picture, same motion, no repaint.

Two obligations come with it. Honour prefers-reduced-motion — for a real number of people parallax is not a flourish, it is nausea, and the whole cost of respecting it is a three-line media query that sets animation:none and leaves every star exactly where it is. And do not leave will-change on things that are not changing: it promotes a layer and holds memory, so it is a promise about the next few seconds, not a decoration.

left is a layout property: every frame the engine recomputes the panel’s box, which can reflow its siblings and its descendants, then repaints, then composites. transform touches none of that — the layer is already painted, and the frame is a matrix applied to it on the compositor thread. The panel is not moving in layout at all; nothing around it can notice.

What you had to check: transform makes a stacking context (chapter ten), so anything inside the panel that was escaping via z-index no longer can. And a transformed element is still where it was for layout purposes — it does not push siblings, and its hit area moves with it but the space it reserved does not, which is a feature for an overlay and a bug for a list item.
