Everything in this yard computes, holds state, and moves documents between pages without running a line of script. This page is the how. Six techniques, each with a working example beside it — the examples are the real thing, not screenshots. Press the buttons.

One · counters are arithmetic

lesson oneThe browser will add up for you

Every checked option increments a counter; an element further down the document prints the sum. That is real addition done by the layout engine — no state, no handler, no framework. The catch is the only one that matters: document order. A counter can only be printed after the things that increment it, which is why every board in this yard puts its inputs before its totals and uses CSS grid to put the totals back on the right.

CSS adds. It does not multiply, subtract, or take a minimum. Anything that needs those has to be stated outright — which is a discipline, not a limitation: a number you had to write down is a number someone can check.

body{counter-reset: crates 0 tons 0}
#q2:checked + label{counter-increment: crates 2 tons 80}
.total::after{content: counter(crates)}

Two · :has() is state

lesson twoA parent can look at its children

:has() lets a rule match an ancestor by what is inside it, which means a hidden radio anywhere in a container can style anything else in that container. That is a state machine: the radios are the state, the rules are the transitions, and there is nothing to keep in sync because there is only one copy of the truth.

The one trap: the switch and the thing it drives must share an ancestor you can name. Scope from that ancestor, not from whatever is nearest the switch — half a day was lost in this yard to a rule scoped to a row when the hulls it moved were in a different subtree entirely.

.board:has(#s-open:checked) .shut{display:none}
.board:has(#s-shut:checked) .open{display:none}
◻ ◻   the door stands open ◼◼   the door is shut

Three · compound :has() is a two-key lookup

lesson threeTwo questions, one answer

Chain them — :has(A):has(B) — and you have a lookup table keyed on a pair. Neither input could produce the value alone: a hull does not know its own draft state, and a draft state does not know which hull it is on. Write one rule per cell and the pair answers.

It costs rules. Ten hulls by three drafts is thirty rules and there is no shortcut, which is the honest trade: the table is visible, auditable, and every number in it was written by someone. Nothing is inferred behind your back.

.board:has(#h-a:checked):has(#d-half:checked)
  .look::after{content:"116"}

Four · animation-play-state is a stop

lesson fourMotion, and the authority to end it

An animation's duration is a speed control and animation-play-state: paused is a brake — and because both are ordinary properties, anything that can match the element can apply them. Put the stop rule last in the cascade and it wins over every speed rule beneath it, which is how you build a hold that cannot be argued with by something further down.

Green, red, blue, yellow along the whale's flank are the same idea: four states, one property, no logic. Red is not a slow speed. It is a different kind of thing, and the cascade is where you say so.

.l4:has(#go-fast:checked) .runner{animation-duration:1.6s}
.l4:has(#go-stop:checked) .runner{animation-play-state:paused}
/* written last, so it beats every speed above it */

Five and six · transport, and data that is not code

lessons five and six How a page with no script sends something to another page

A GET form is transport. Give the inputs names and values, point the form at another file, and the browser serialises everything checked into the address bar and opens it. The sending page does nothing — it does not have to know how, because encoding a form is something browsers have done since before any of this. The receiving page reads location.search. That is the entire API: no fetch, no endpoint, no server, no library.

<form action="bridge.html" method="get">
  <input type="radio" name="class" value="cruiser" checked>
  <button>Send</button>
</form>
→ bridge.html?class=cruiser

And <script type="application/json"> is data. The browser parses it as a data block and never executes it — a safe place to park a document inside a page. Print the same text beside it and the reader can see exactly what is being carried. In this yard the cargo page keeps its manifest in one, mirrors it in a <pre>, and posts the identical string in a hidden field. All three were checked byte-for-byte before it shipped, because "what you see is what goes" is only true if someone verified it.

The structure · SPQR over sergeant over corporal

SPQR

The assembly sets the frame

Outermost and written first. What it declares is inherited by everything beneath it, and a rank below can only depart from it by saying so explicitly, in the open, where the departure is visible.

Sergeant

The sergeant reads the gap

Nested inside, and closer to the work. Overrides what the frame left open and passes the rest down untouched — most of what it does is decide what not to change.

Corporal

The corporal holds the rear guard

Innermost: nearest the work, first to know, and the easiest to overrule — anything written outside it can reach in. Which is the point. The rank doing the work is not the rank that gets to decide it is finished.

There is no code behind that hierarchy. It is nesting and the cascade — outer written first, inner overriding, and every override sitting in the stylesheet where anyone can read what was changed and by whom. A chain of command is a specificity order with names on it.
