Learn

HTML and CSS can compute, hold state, and hand work between pages with no script at all. This is how — and then, at more length, nine mistakes that were really in these files, with the code that was wrong and what fixed it. The second half is the useful half.

Part one · the technique

the one ruleDocument order is the constraint

A CSS counter can only be printed after the things that increment it. Everything else about these pages is arranged around that single fact: inputs come first in the markup, totals come after, and the layout is put back the way you want it with grid. Fight this and nothing works; accept it and the rest is easy.

body{counter-reset: crates 0}
#q-2:checked + label{counter-increment: crates 2}   ← must come first in the DOM
.total::after{content: counter(crates)}          ← and this after
crates
tonnes

the limitsCSS adds. That is all it does.

No subtraction, no multiplication, no division, no minimum. This is not a gap to route around cleverly — it is the shape of the tool, and the honest responses are:

Need a product? Write the products out. Three options by three states is nine rules, keyed on a pair with :has(A):has(B). There is no shortcut and the table is better for it: every cell was written by somebody who can be asked why.
Need a difference? Declare it, or print both numbers and say why the difference is absent. Never let a figure appear as if the page computed it when it did not.

state:has() lets a parent see its children

A hidden radio anywhere inside a container can style anything else in that container. That is a whole state machine with nothing to keep in sync, because there is only one copy of the truth — the DOM.

.scoped:has(#s-on:checked) .lamp{background:var(--good)}

authorityWhat is written last, wins

Equally specific rules resolve by order. So the thing that must not be overridden goes at the bottom of the stylesheet. A stop written above a speed is a suggestion; written below it, it is a stop.

.casc:has(#g-fast:checked) .mv{animation-duration:1s}
.casc:has(#g-stop:checked) .mv{animation-play-state:paused}  ← last, so it wins

transportA GET form is an API call

Give inputs names and values, point a form at another file, and the browser serialises everything checked into the query string and opens it. The sending page does nothing. Add form="id" to associate an input with a form anywhere in the document, so your markup does not have to be reorganised around it.

<form id="vy" action="bridge.html" method="get"></form>
<input type="radio" name="class" value="cruiser" form="vy" checked>
<button type="submit" form="vy">Send</button>
→ bridge.html?class=cruiser

Part two · nine things that were wrong in these files

Each of these shipped, or nearly did. The code is the actual code.

mistake oneA :has() scoped to the wrong subtree

wrong 
.row:has(.k-red:checked) .ship{animation-play-state:paused}
Symptom: nothing happened. No error, no warning — the rule simply never matched, which is the worst kind of failure because it looks like the property is unsupported.

The switches were in a .row in the switchboard. The hulls were in a completely different part of the document. A descendant combinator cannot cross to a sibling subtree.

right 
.board:has(#c1r:checked) .sh1{animation-play-state:paused}

The rule to remember: scope from the nearest ancestor that contains both the switch and its target — not from whatever element happens to be near the switch.

mistake two alternate plays your keyframes backwards

wrong 
.ship{animation: run 19s linear infinite alternate}
@keyframes run{from{left:0} to{left:calc(100% - 64px)}}
Symptom: every ship sailed the return leg stern-first. Obvious once seen, invisible while writing it.

alternate does not "go back" — it replays the same frames in reverse, including everything you did not think of as directional.

right 
@keyframes run{
  0%  {left:0;                 transform:scaleX(1)}
  49% {left:calc(100% - 64px); transform:scaleX(1)}
  50% {left:calc(100% - 64px); transform:scaleX(-1)}   ← comes about
  99% {left:0;                 transform:scaleX(-1)}
  100%{left:0;                 transform:scaleX(1)}}

Write the whole cycle out. And remember the duration now covers a round trip, so double it to keep the same speed — I missed that the first time too.

mistake threeA total that could only ever grow

wrong 
#v-2:checked+label{counter-increment: cr 1840 net 1840}
#o-wage:checked+label{counter-increment: dr 2400}
.balance::after{content: counter(net)}      labelled "net position"
Symptom: none. It rendered perfectly and was wrong — the "net" was gross credits with the debits silently missing, because a counter cannot go down.
right 
Show both, and say why the difference is absent:
<div>Taken in <b class="n-cr"></b>, against <b class="n-dr"></b> paid out</div>
<p>The difference is not printed. CSS adds and cannot subtract, and this
   page will not show a figure it did not compute.</p>

This is the one worth internalising. A wrong number that renders beautifully is more dangerous than a broken layout, because nothing about it looks like a bug.

mistake fourAn interlock a keyboard walks straight around

wrong 
.board:not(:has(#k-arm:checked)) .throw label{pointer-events:none}
Symptom: the mouse could not reach the kill switch. The Tab key could. So could a browser restoring form state on reload.

pointer-events is about pointers. It is not access control, and a safety interlock that only stops a mouse is decoration.

right 
.board:not(:has(#k-arm:checked)) .throw label{opacity:.32;pointer-events:none}
.board:not(:has(#k-arm:checked)) #k-throw{visibility:hidden}   ← out of tab order

and every consequence names both inputs, so a restored state cannot fake it:
.board:has(#k-arm:checked):has(#k-throw:checked) .ship{animation-play-state:paused}

Then check all four input combinations, not just the two you were thinking about.

mistake fiveInline styles faking a class

wrong 
<i class="b on" style="background:var(--red);box-shadow:0 0 10px var(--red)">
Symptom: it looked right. It was a blue lamp wearing red paint, so nothing could select it as red and the next change broke it.
right 
.lamps i.on.r{background:var(--red);box-shadow:0 0 10px var(--red)}
<i class="r on">

When you find yourself writing an inline style to say what a thing is, you wanted a class.

mistake sixA non-greedy regex that stopped too early

wrong 
s.replace(/\.board:has\(#o-a[\s\S]*?content:"0"\}/, replacement)
Symptom: two stale rules survived into every generated file, referencing ids that no generated board had. Harmless until a board used those ids, and then silently wrong.

The block being replaced contained content:"0" in the middle, so the lazy quantifier stopped there instead of at the end.

right 
anchor on something that only appears at the end:
s.replace(/\.board:has\(#o-a[\s\S]*?#o-c:checked\):has\(#s-off:checked\)[^}]*\}/, r)

Then count the output. 6 rules in, 8 rules out is how this was caught — not by reading it.

mistake sevenReading a computed style mid-transition and believing it

wrong 
el.checked = true;
await sleep(400);
getComputedStyle(ship).opacity   → "0"  … so the rule must be broken?
Symptom: I "found" three bugs that did not exist and nearly rewrote working CSS to fix them.

The element had transition: opacity .3s. The read landed mid-flight, or before the engine had recalculated at all — so the number was true and meaningless at the same time.

right 
el.checked = true;
for (let i=0;i<3;i++){ document.body.offsetHeight;      force a reflow
                       await new Promise(requestAnimationFrame); }
await sleep(450); document.body.offsetHeight;
getComputedStyle(ship).opacity   → "1"  — the truth

Verification has its own bugs. A test that lies costs more than no test, because you act on it.

mistake eightA file describing itself as it used to be

Symptom: the comment at the top of the lane board said "the run has no blocker in it anywhere… the only way to stop them is to close the page." A kill switch had been wired in an hour earlier.

Documentation does not rot gently; it becomes a confident lie. The header was the most authoritative text in the file and it was the wrong text. Prose that describes behaviour is part of the behaviour — when the code changes, it is not finished until the sentence about it changes too.

mistake nine git add -A in a repository you did not survey

wrong 
git add -A && git commit -m "..."     → 240 unrelated files, 2 embedded repos
Symptom: a two-file change became a commit containing most of a home directory.
right 
git add bridge.html cargo.html manifest.example.json
and to undo it before anyone pulls:
git reset --soft HEAD~1 && git reset

Name your files. It takes four seconds and it is the difference between a commit and a landslide.

Part three · what to do next

exercisesOn template.html, in this order

  1. Move the totals above the inputs. Watch every number go to zero. That is the one rule, felt rather than read — put them back.
  2. Add a fourth option to the choice group. You will write two more lookup rules by hand. That cost is the honest price of a language with no multiplication.
  3. Move the stop rule above the speed rule in the cascade. It stops working. Move it back.
  4. Break a :has() on purpose — scope it to the row instead of the board — so you recognise the silence when it happens for real.
  5. Try to display a difference between two counters. You cannot. Decide what you will show instead, and write the sentence explaining it.
  6. Tab through your page with the mouse untouched. Everything reachable? Everything that should not be, unreachable?

checklistBefore anything ships

1. Totals appear after every input that feeds them.
2. No number on the page is one the page did not compute.
3. Every :has() is scoped to an ancestor of both the switch and its target.
4. Anything that must not be overridden is written last.
5. Guards work for the keyboard, not only the pointer.
6. Focus outlines still present; prefers-reduced-motion honoured.
7. The comment at the top still describes the file as it is now.
8. You counted the output rather than reading it.

The through-line. Six of these nine mistakes rendered perfectly while being wrong. That is the thing to take from this — in a language with no runtime and no error messages, "it looks right" is not evidence of anything, and the discipline that matters is deciding what would prove it and then going and checking. The patterns in part one you will pick up in an afternoon. Part two is the part that takes a while.
